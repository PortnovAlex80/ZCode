# Следующий этап: harness артефакта

Дата: 2026-10-15. Статус: пользователь поручил реализацию;
[MD/TXT MVP](ARTIFACT-HARNESS-MVP.md) фиксирует текущий объём и проверку на
титульном листе ОДН. Развивает U-02 из [чеклиста](IMPLEMENTATION-CHECKLIST.md).

## Суть идеи

У файла, документа, папки и корня проекта есть собственный паспорт: что это,
для чего нужно, на какие источники опирается, как с этим работать и как проверить
результат. Агент получает этот контекст при работе с выбранным артефактом.
Проект остаётся окружением работы; предметом конкретного поручения становится
артефакт с явно указанными границами изменений.

Скиллы и чеклисты — часть паспорта. Скилл объясняет метод работы, чеклист задаёт
критерии, паспорт связывает их с конкретным объектом, источниками и результатами.
Текст инструкции сам по себе не запускает проверку и не подтверждает готовность.

Практическое отличие от одного скилла: скилл — переиспользуемая методика,
паспорт — её привязка к конкретному артефакту, входам, шаблону и критериям.
Если хранить лишь копию скилла, дополнительной пользы почти нет. Цель — короткое
поручение «обнови титул» с автоматически собранным, видимым пользователю контекстом.

В паспорте описываются шаги: действие, вход, инструмент, ожидаемый результат и
поведение при ошибке. Ссылка на инструмент содержит file/MCP/REST, логическое
подключение и операцию. Адреса, stdio/HTTP, авторизация и разрешения остаются у
существующей интеграции и runtime ZCode. Паспорт не создаёт транспорт и не является
новым исполнителем workflow. Недоступное подключение нельзя подменять выдуманным.

Активация — меню Context в шапке обсуждения: без метаданных, использовать,
посмотреть собранный контекст, редактировать. Снимок перечитывается на каждом
новом сообщении; его отключение не удаляет ранее отправленный контекст из истории.

Первый предметный сценарий — титул записки опоры ОДН: TXT с реквизитами,
MD-шаблон, рабочий MD, правила проекта/папки/файла и ссылка на навык оформления.
Учебный комплект: `examples/artifact-harness-odn`. Неизвестные реквизиты явно
показываются, авторский текст сохраняется; расчёты, нормативная приёмка и PDF-вёрстка
проверяются отдельными действиями. Реальные данные проекта в пример не копируются.

Пример: у `расчёт-фундамента.md` указаны назначение записки, версия геологии,
связанная расчётная модель, методика расчёта, навык подготовки записки и чеклист
проверки нагрузок, единиц и ссылок на результаты. Для агента поручение «обнови
записку» получает этот контекст, а не только общий набор правил репозитория.

Концепт рабочего места строится вокруг инженерного объекта и состояния работы:
объект → подтверждённые исходные данные → варианты → расчёт → проверки → документы
→ выпуск. Карточка объекта показывает входы, результаты, связи и недостающие этапы;
ИИ помогает внутри этого процесса. Детерминированное «Рассчитать» вызывает solver
через типизированный сервис без обязательного LLM-запроса. Завершение задания,
инженерный вердикт и актуальность результата — разные состояния.

Паспорта — нижний слой такой среды: привязка документа/объекта к входам, навыкам,
процедурам и критериям. Они не заменяют отдельное состояние объекта, подтверждение
входов, владельца solver jobs, сравнение вариантов или выпуск. Следующая возможная
вертикаль после титула — карточка опоры с разделами «Данные / Варианты / Проверки /
Документы» и действиями в соответствующем разделе. Реализация этой оболочки не
включена в текущую сборку. Найденный прототип фундамента также не доказывает полной
готовности native desktop, инженерной квалификации или релизной поставки.

## Состав паспорта

| Часть | Содержание |
| --- | --- |
| Идентичность | Стабильный ID, вид объекта, расположение, версия формата паспорта |
| Назначение | Что это за результат, кому нужен, область работы |
| Основания | Источники и их версии, связанные артефакты, происхождение данных |
| Метод работы | Ссылки на навыки, методики, шаблоны; локальные уточнения |
| Границы | Что разрешено менять в рамках поручения, что требует отдельного решения |
| Готовность | Чеклист, автоматические проверки, ручная приёмка |
| Доказательства | Результат проверки и точная редакция артефакта/входов, к которой он относится |

Общие навыки и методики можно подключать из версионированного предметного пакета.
Паспорт конкретного файла хранит привязки и уточнения. История чата, токены,
настройки аккаунтов и тяжёлые результаты расчётов в паспорт не включаются.

## Как агент будет использовать паспорт

1. Поручение явно связано с выбранным артефактом; UI показывает объект и проект.
2. Сервис собирает применимые правила проекта, родительских папок и самого
   артефакта. Показывает происхождение каждого правила и конфликты.
3. В контекст поступают паспорт и нужные для поручения инструкции. Содержимое
   всех связанных файлов автоматически целиком не подгружается.
4. Агент выполняет поручение через существующий runtime и разрешённые инструменты.
5. Проверки записывают доказательства для конкретной редакции. Изменение входов
   делает зависимые результаты устаревшими; ручная приёмка остаётся отдельной.

Правила артефакта уточняют общие правила, но не расширяют разрешения инструментов
и не отменяют обязательные ограничения проекта. Импортированные инструкции
должны иметь видимый источник и проходить принятие пользователем перед активацией.
Автоматическое исполнение команд из найденных метаданных не предполагается.

Точный контракт наследования, конфликтов и владения записью требуется оформить
перед реализацией. Это план поведения, а не уже принятая новая схема хранения.

## Что значит «метаданные путешествуют с артефактом»

Один центральный `.harness/project.json` подходит для существующего хранения,
но копирование одного файла в Проводнике не переносит его паспорт автоматически.
Нельзя обещать переносимость, пока не реализован явный механизм.

Целевые сценарии:

- Перенос всего проекта: относительные ссылки работают после смены корня.
- Перемещение/переименование внутри проекта: паспорт следует за объектом;
  неоднозначные внешние перемещения требуют перепривязки, без угадывания по имени.
- Копирование как нового артефакта: новый ID с указанием происхождения;
  прежние результаты проверки не становятся автоматически принятыми.
- Экспорт выбранного артефакта: файл/папка, паспорт и необходимые локальные
  зависимости входят в переносимый комплект; внешние зависимости перечислены.
- Импорт: видны недоступные источники, конфликтующие ID и правила до активации.

До разработки экспорта сравнить sidecar рядом с файлом, пакет экспорта и реестр
проекта; оформить ADR с единым владельцем записи и миграцией текущего формата.
Встраивание метаданных внутрь DOCX/PDF/DWG не является обязательным условием MVP.

## Приёмка

- [ ] Два файла одного проекта получают разные инструкции без смешивания контекста.
- [ ] Для папки/корня видно, какие правила наследуются и откуда они пришли.
- [ ] Повреждённые или недоступные метаданные не подменяются пустыми успешными данными.
- [ ] Rename сохраняет привязку; copy создаёт новую идентичность с происхождением.
- [ ] Пакет открывается в другом каталоге без абсолютных путей исходной машины.
- [ ] Отсутствующий навык/источник виден до выполнения зависимого действия.
- [ ] Обновление артефакта/входов не оставляет устаревшие проверки зелёными.
- [ ] Импорт не активирует инструкции и команды без принятия пользователем.
- [ ] Существующие выбор модели, авторизация, история и разрешения сохраняются.
