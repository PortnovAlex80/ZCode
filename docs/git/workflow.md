# Работа с Git в форке ZCode

Действует с 2026-10-18. Общие правила для Codex, Claude и других агентов.
Развивает политику двух веток из
[плана поставки](../spec-harness/IMPLEMENTATION-PLAN.md).

## Ветки и рабочие каталоги

- `dev` — основная рабочая ветка. Обычные задачи выполняются в существующем
  `D:\Development\ZCode-Harness`, без новой ветки на каждый запрос.
- `master` — принятые версии. Перевод `dev` в `master` выполняется отдельно,
  после приёмки и в рамках разрешения пользователя, через fast-forward.
- По умолчанию один checkout и никаких дополнительных worktree, клонов,
  detached HEAD или веток `task/*`, `agent/*`, `fix/*`.
- Исключение — прямое указание пользователя для конкретной задачи. До создания
  временного дерева фиксируются его владелец, цель, базовая ревизия и условие
  удаления. Постоянные дополнительные ветки не создаются.
- Правило распространяется на автоматически предлагаемые skill/plugin-процессы.
  Несколько агентов работают в общем дереве с непересекающимися файлами;
  пересекающиеся изменения выполняются последовательно. Индексом и Git refs
  управляет один координатор.

## Начало работы

Проверить `git status --short --branch`, `git diff --cached --stat`,
`git branch -vv` и `git worktree list`; прочитать применимые AGENTS.md.
Запомнить исходные чужие изменения и текущую ревизию. Не делать автоматические
checkout, pull/rebase, stash, reset или clean ради получения «чистого» дерева.
При появлении чужих изменений в своих файлах сначала установить их происхождение.

## Коммиты — часть завершения задачи

Завершённая реализация включает код, необходимые тесты и документацию, проверки
и Git-коммит. Отдельного напоминания «теперь закоммить» не требуется.
Исследование без изменений, явная просьба не коммитить или конкретный блокер
проверки/владения — исключения; в ответе должно быть прямо сказано, что коммита нет
и почему. Не объявлять непроверенную реализацию законченной.

Один коммит — одно проверяемое намерение. Исправление, его регрессионный тест
и нужное изменение спецификации идут вместе. Не смешивать с ним посторонние
рефакторинги, форматирование или пользовательские правки. Отдельная политика Git
или запись результатов поставки может быть отдельным коммитом. Долгая работа
разбивается на законченные проверенные части, а не на коммиты после каждого файла
или в конце нескольких несвязанных задач.

Перед коммитом:

1. Выполнить проверки, соответствующие изменению и правилам AGENTS.md. Не повторять
   уже успешные дорогие проверки без новых изменений или обнаруженной проблемы.
2. Добавить только свои явные пути или hunks. Не использовать `git add .` /
   `git add -A` в общем грязном дереве. Не коммитить чужой заранее заполненный индекс.
3. Проверить `git diff --cached --stat`, сам staged diff и
   `git diff --cached --check`. Не включать установщики, `.tmp`, логи, профили,
   секреты и пользовательские данные.
4. Создать Conventional Commit по
   [существующей инструкции](ai-agent-commit-message-guidelines.md): результат
   в заголовке, причина и существенные проверки в теле. Не обходить hooks через
   `--no-verify`. Без отдельного разрешения не делать amend/rebase опубликованных
   коммитов и force-push.
5. Проверить фактический hash и остаточный `git status`. В конце сообщить commit
   hash, выполненные проверки, оставшиеся чужие изменения и факт push/его отсутствия.

Push не является синонимом commit. Публикация, удаление удалённых веток и продвижение
`master` выполняются только в рамках разрешения пользователя в текущей сессии.

## Сборки и поставка

Сначала проверить и закоммитить исходники поставляемого изменения, затем собирать
приложение: встроенный `buildCommitId` должен указывать на зафиксированный код.
Посторонние изменения не стирать; до сборки проверить, могут ли они попасть в её
входные файлы. Не называть сборку чистой только по наличию commit ID.

Результаты упаковки и GUI-приёмки можно записать следующим документационным
коммитом без повторной упаковки неизменного приложения. Указывать настоящий hash
исходной сборки, контрольную сумму артефакта и границы приёмки. Не исправлять номер
версии или встроенную ревизию уже готового приложения вручную.

## Завершение временной ветки или worktree

После интеграции проверить, что нужные коммиты достижимы из `dev`. Полностью
слитые локальные ветки удалять через `git branch -d`; временные worktree — через
`git worktree remove` после проверки отсутствия незакоммиченной работы.
Не применять `--force`, reset или удаление каталога для обхода грязного дерева.

Неслитую работу не выдавать за интегрированную. Если пользователь поручил уборку,
сохранить её под отдельным архивным тегом, записать исходную ветку и полный hash,
проверить, что тег указывает на тот же коммит, и только потом удалять ветку.
Архив не публикуется автоматически. Если безопасная уборка невозможна, сохранить
работу и явно указать оставшееся дерево/ветку вместо уничтожения данных.
